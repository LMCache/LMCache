## Codebase Patterns
- Recipe structure: Follow R-001 (dense_instruct_cpu_hot_cache.md) as the golden template
- YAML configs: Keep in separate .yaml file with matching base name
- Benchmarks: Use `vllm bench serve` with `prefix_repetition` dataset for cache validation
- Always set PYTHONHASHSEED=0 for deterministic chunk hashing
- Critical sizing guidance: CPU cache should be 1.5x GPU KV cache budget
- Include both cold and warm request validation with actual log snippets
- Comparison table should include: no caching, LMCache only, native prefix caching
- SGLang uses `--enable-lmcache` flag and `LMCACHE_CONFIG_FILE` env var (same YAML format as vLLM)
- Disk persistence recipe focuses on restart survivability, not just speed
- Always document disk path setup (mkdir, chown, permissions)
- Disk backend uses `local_disk: true` + `local_disk_path` + `max_local_disk_size`
- Redis remote backend uses `remote_url: redis://host:port` format
- Redis recipe must include setup instructions (apt install, Docker, cloud)
- Cross-instance sharing requires identical `chunk_size` across all instances
- Document Redis connection URL formats including authentication
- LMCache Server uses `remote_url: lm://host:port` format
- LMCache Server is started via `python -m lmcache.server`
- Include comparison table when there are similar alternatives (Redis vs LMCache Server)
- Multi-instance recipe should show architecture diagram (ASCII art)
- Demonstrate three phases: cold (Instance A), remote hit (Instance B first), local hit (Instance B second)
- Include Kubernetes deployment pattern for production relevance
- Cache warming pattern is valuable for production deployments
- PD mode uses `enable_pd: true` with `transfer_channel: nixl`
- PD requires separate configs for sender (prefill) and receiver (decode)
- PD mode cannot be combined with Storage Mode backends
- Document PD constraints: no persistence, eager mode required, no prefix caching
- Compare PD vs Storage Mode to help users choose
- Multi-node PD requires TCP in NIXL backends for cross-node transfer
- Proxy server uses CSV format for multiple hosts: `--prefiller-host "ip1,ip2"`
- Session affinity via `CLIENT_BOUND` env var for multi-turn conversations
- Tiered storage uses both `local_cpu: true` AND `local_disk: true`
- Size CPU tier for hot data (~70% working set), disk for full working set
- Document tiering behavior: hot (CPU) vs warm (disk) vs cold (compute)
- Production checklist is valuable for deployment verification
- Production Stack Helm values enable LMCache via `servingEngineSpec.modelSpec[].lmcacheConfig`
- KServe integration uses ConfigMap-mounted LMCache YAML + `LMCACHE_CONFIG_FILE`
- llm-d ModelService can enable LMCache with `modelCommand: custom` and inline config
- Redis Sentinel uses `redis-sentinel://host1:port1,host2:port2,.../service_name` URL format
- Redis Cluster uses `redis-cluster://host1:port1,host2:port2,...` URL format
- Valkey uses `valkey://host:port` with auth in `extra_config`
- S3 backend requires `extra_config.s3_region` and `save_chunk_meta: false`
- MooncakeStore uses `mooncakestore://host:port` plus required extra_config fields
- InfiniStore uses `infinistore://host:port?device=...` and `infinistore_link_type`
- P2P sharing requires `enable_p2p` + `enable_controller` with unique init/lookup ports
- Controller API provides `/move` and `/health` endpoints for orchestration
- PD tuning uses `pd_buffer_device` and `pd_buffer_size` as primary stability knobs
- CacheGen compression is enabled via `remote_serde: "cachegen"` for remote backends
