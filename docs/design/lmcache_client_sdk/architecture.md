# lmcache-client-sdk: standalone engine-facing client

## Motivation

`LM-968` asks for a lightweight client package that an inference engine can
embed on its runtime path. The existing `lmcache.sdk` orchestrates offline,
batched KV conversion (the token-dropping pipeline: `LMCacheBatchedStream`
prefill/modify/decode, edit functions, and qcache intermediate tensors), and
the multiprocess server exposes cache-dropping internals such as
`end_session` block release and the QRingBuffer. Neither matches the need:
an engine wants a thin, frozen client contract — connect, store, retrieve,
session — that stays byte-compatible with the running server and never has to
change when the server adds features.

This package, `lmcache-client-sdk`, is that client. It is deliberately
separate from the token-dropping SDK and contains **no cache-dropping
operations**: `end_session` here only terminates a LOOKUP session and cleans
server-side session state; it never frees blocks.

## Package boundary

| Included | Excluded |
|---|---|
| Engine-driven register/unregister | Token-dropping offline conversion (`LMCacheBatchedStream`, edit functions, qcache) |
| `store` / `retrieve` for KV cache tensors | Cache dropping (block release, QRingBuffer) |
| LOOKUP / prefetch-status session flow | Hybrid multi-kernel-group layouts |
| `connect` / `close` lifecycle | Writing to server storage outside the engine-driven flow |

## Repository layout

The package lives at the repository root as a self-contained directory so it
ships without dragging in the ~5000-line in-process server stack:

```
lmcache_client_sdk/
    __init__.py       # public entry: connect(), LMCacheClientContext
    context.py        # store/retrieve/session orchestration
    transport.py      # synchronous ZMQ (DEALER) wire client
    protocol.py       # frozen msgspec wire structs for the engine-driven RPCs
    tensor_wire.py    # typed inline tensor envelope (encode/decode + validation)
    server_config.py  # /config, /status discovery + shape reverse-parsing
    key.py            # IPCCacheServerKey (packed token bytes) contract
    token_codec.py    # big-endian uint32 token packing
    logging.py        # stdlib-only init_logger
    _version.py       # generated by setuptools_scm
```

## Wire protocol contract

The client speaks the multiprocess wire protocol directly, so it works
against any server that implements it, without importing `lmcache` itself.

- **Frames**: request `[request_uid, operation, *payloads]`, response
  `[request_uid, operation, *response]`, all MessagePack-encoded, over
  ZMQ ROUTER/DEALER. A DEALER socket is used (not REQ) because REQ inserts an
  extra empty delimiter frame that shifts the ROUTER-side layout.
- **Operations**: addressed by stable snake-case string names
  (`register_kv_cache_engine_driven_context`, `lookup`,
  `query_prefetch_status`, `prepare_store`, `commit_store`,
  `prepare_retrieve`, `commit_retrieve`, `end_session`,
  `unregister_kv_cache_engine_driven_context`, plus `get_chunk_size` /
  `ping`).
- **Hashing**: chunk hashes are computed **server-side**; the client only
  packs token ids into `token_bytes` (big-endian `uint32`).

## Geometry discovery

The server's HTTP endpoints provide everything the client needs:

- `/config` → `mp.chunk_size` (tokens per chunk).
- `/status` → `cache_context_meta[model_name]` with `world_size`,
  `num_kv_readers`, and `kv_cache_layout` (a single kernel group: `dtype`,
  `tokens_per_block`, `engine_kv_format`, `engine_kv_concrete_shape`,
  `is_mla`).

The concrete shape string is decoded by walking the same format-name
template the server renders it from (e.g. `NL_X_TWO_NB_BS_NH_HS` →
`80 x [2, 2048, 16, 8, 128]`): the `_X_`-separated prefix is the outer level,
the final `_`-joined segment labels the bracketed inner dimensions, with
`ONE`/`TWO`/`NP` treated as literals. From the labels the client recovers
`block_size`, `num_kv_heads`, `head_dim`; `hidden_dim_size` is
`num_kv_heads * head_dim` (split K/V) or `head_dim` (MLA/single-plane).

## Store / retrieve flow

```
connect(url, http_url, model_name)
  ├─ /config + /status → chunk size, layout geometry
  ├─ instance_id (63-bit uuid)
  └─ register_kv_cache_engine_driven_context(...) → null_block_id

store(kv, tokens)
  ├─ chunk-align tokens, copy KV to CPU
  ├─ prepare_store(key, instance_id)
  ├─ slice per-chunk tensors → encode_tensors() → commit_store(key, ...)
  └─ end_session(request_id)

retrieve(tokens)
  ├─ submit LOOKUP (worker_id-less key) → poll query_prefetch_status
  ├─ prepare_retrieve(key) → decode_tensors(validated envelope)
  ├─ concatenate chunks along the token axis (ndim - 2)
  ├─ commit_retrieve(key)
  └─ end_session(request_id)
```

Retrieval is all-or-nothing: a miss or a partial prefetch returns `None` and
the session is closed.

## Packaging and release

Mirrors the existing `lmcache-cli` publishing pattern:

- `pyproject_client_sdk.toml` — `name = "lmcache-client-sdk"`, dynamic
  dependencies from `requirements/client_sdk.txt`
  (`torch >= 2.0`, `requests`, `msgspec`, `pyzmq`), `setuptools_scm`
  with `no-local-version`, package discovery limited to
  `lmcache_client_sdk`.
- `.github/workflows/build_client_sdk_artifacts.yml` — copies
  `pyproject_client_sdk.toml` → `pyproject.toml`, builds a pure-Python wheel,
  verifies no `.so`/native extension, and runs the unit tests
  (`tests/lmcache_client_sdk/`) plus an import smoke test.
- `.github/workflows/publish.yml` gains `build-client-sdk` and
  `publish-client-sdk-test-pypi` / `publish-client-sdk-pypi` jobs, gated by
  the same paths-changed filter extended to the new files.

## Testing strategy

Tests live under `tests/lmcache_client_sdk/` and only exercise public entry
points (`connect`, `store`, `retrieve`, `close`) against an in-memory mock
server (`mock_server.py`) that implements the HTTP endpoints and the ZMQ RPC
frame contract:

- codec, key, wire-format, and shape-parsing unit tests;
- an end-to-end store→retrieve roundtrip through the mock server;
- failure paths: unregistered model, token-count mismatch, empty retrieval.

They run under `pytest --confcutdir=tests/lmcache_client_sdk` so the
repository-level GPU fixtures are never loaded.

## Known limits

- Hybrid models with more than one kernel group are rejected explicitly
  (client raises instead of silently mis-storing).
- `engine_kv_concrete_shape` parsing is template-based and relies on the
  server reporting the format name; a mismatch raises a clear error.
- The client is synchronous by design; engines needing async pipelining
  should wrap it (the RPC surface is stable).
